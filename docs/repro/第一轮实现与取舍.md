## 本轮交付

只有两个包：`protocol` 定义共同语言，`rules` 用纯函数评估请求。
另有 `examples/rules-demo.ts`，执行 `pnpm demo` 即可演示，不需要密钥或账号。
命令字符串只作为输入数据，程序不会执行这些命令。

这还不是 M1 的完整审批闭环。真实 ACP 进程、主人身份校验、重复回调、SQLite、飞书均未实现。
后续新包会依赖本轮的契约；目前没有需要同步更新的 ACP 客户端、导出器或渠道实现。

## 先沿一条请求读代码

打开 `examples/rules-demo.ts`，找到 `pnpm test --run`：

1. 演示将它包装成一个 `Item`。`id` 标识条目，`cwd` 表示项目目录，`toolCall` 描述操作。
2. `evaluateRules` 检查它是不是一个打开的权限条目。
3. `guardCheck` 检查敏感路径、提权、强推、危险删除等条件。命中立即返回 `escalate`。
4. `matchRules` 查找主人配置的规则。它记住第一条允许规则，但继续寻找拒绝规则。
5. 匹配 `allow-tests` 后返回 `allow` 和规则来源；演示将结果打印出来。

把输入换成 `git push --force`，第 3 步就结束，规则根本不会运行。
把输入换成 `git status`，没有匹配规则，最终返回 `escalate`，意思是需要主人决定。

`RuleEvaluation` 是本轮的评估结果。`Decision` 是将来保存最终决定时使用的协议类型。
将来的核心负责把建议、运行模式和主人的回答组合起来，不能把演示中的 allow 直接当成执行授权。

## 文件各负责什么

| 文件 | 责任 | 值得理解的点 |
| --- | --- | --- |
| `packages/protocol/src/types.ts` | 共享类型 | interface 描述对象；联合类型限制可用状态 |
| `packages/protocol/src/channel.ts` | 最小渠道契约与输入校验 | TypeScript 类型运行时不存在，外部数据从 unknown 开始 |
| `packages/rules/src/evaluate.ts` | 串起守卫、规则、交给主人 | 用提前返回写清业务优先级 |
| `packages/rules/src/guard.ts` | 内置与额外守卫 | 额外守卫只能增加限制，异常不会放行 |
| `packages/rules/src/match.ts` | 匹配条件及冲突处理 | deny 优先；同动作使用第一条 |
| `packages/rules/src/shell.ts` | 读取单词、引号和连接符 | 状态变量表示“当前是否在引号里”，不尝试执行 shell |
| `packages/rules/src/normalize.ts` | 命令归一化与显示标签 | 引号内空格保留，归一化不能用来证明安全 |
| `packages/rules/src/paths.ts` | 解析路径、判断目录包含关系 | 用 relative 判断目录层级，不能直接 startsWith |
| `packages/rules/src/scope.ts` | 检查规则的路径范围 | 同时检查 Agent 上报路径和命令参数 |
| `packages/rules/src/redact.ts` | 清理敏感文本 | 已知格式 + 已知环境变量值，日志出口还需要主动调用 |

第一遍只看演示、types、evaluate、match 和 evaluate.test。第二遍再读解析器。
测试中的 `it.each` 表示用一张输入表重复执行同一个测试，并不是额外的业务抽象。

## 本地决定 R001：先做小型确定性规则层

状态：已采用。此记录是本复现项目的设计决定，不修改来源规格的历史结论。

背景：参考文档包含后续桌面产品和多次架构演进，直接照搬会让第一轮难以理解。
本轮选择先把“一个请求为何允许、拒绝或交给主人”做成可测试的函数。

| 选择 | 原因 | 放弃或推迟什么 |
| --- | --- | --- |
| 用普通函数，不引入框架或策略类体系 | 输入输出直接可见，容易单步阅读 | 暂不做动态插件注册 |
| 保留 protocol → 被 rules 引用的边界 | 未来 ACP 和渠道共享类型，避免类型依赖厂商 SDK | 多维护两个很小的包 |
| 不调用模型 | 第一轮行为可重复，不依赖网络和账号 | 暂时无法处理没有规则的新情况 |
| 不实现完整 shell 语法 | 完整解析成本高，误判的代价大 | 某些普通命令也需要主人确认 |
| 路径检查保持纯函数 | 测试可重复，不读取用户文件 | 不解析符号链接，不能当沙箱使用 |

备选方案是直接做 ACP + 飞书纵向闭环，或者复制完整参考架构。
前者第一轮会混入进程、网络、身份验证和存储，后者会制造尚未被需求验证的抽象。
后续每轮加一个可演示的能力，用测试约束已有行为。

## 与参考文档不同的地方

维护者在本轮明确允许不同设计。下面是具体差异，不把来源文档中的已完成状态当作本地事实。

1. 来源计划引用的 Git 基准提交和作者不适用于这个尚无提交的仓库，跳过旧哈希漂移检查和
   指定作者的提交步骤。使用 `codex/round-1-rules` 分支；首次生成后保留改动，
   维护者后续明确要求后再提交。当前未配置远端，未推送或创建 PR。
2. 采用基线的“守卫 → 规则 → 主人”。不采用后来规格中“未命中就自动放行”的行为。
   本轮没有 Reviewer，无法匹配规则就交给主人。
3. 只定义 M1 卡片、文本和动作的渠道契约，暂不定义看板、直连、附件和 pin。
   来源文档没有完整给出 ItemView、SetupUI、MessageRef 等类型的字段，按本轮需求显式补全。
4. 命令归一化保留引号内空格；变量展开、反斜杠、重定向、嵌套脚本、后台执行等写法无法解析。
   命令中的通配符也会交给主人，避免展开后触达敏感目录。
5. 即使归一化能去掉环境变量和 `cd`，允许规则也不会匹配这些原命令。
   `cd /tmp && pnpm test` 不会继承当前项目的允许规则。
6. 路径范围只识别少量常见命令形状。未知命令、未知选项、无法解析的路径不匹配范围规则。
   `pathScope.kind = dir` 必须给出绝对路径。显式上报路径不能掩盖命令参数中的越界路径。
7. 递归删除项目根本身也需要主人。`source`、`xargs` 等间接运行命令的方式统一交给主人。
8. 添加 `evaluateRules` 作为安全组合入口，避免每个调用方都手写守卫和规则的顺序。
   所有异常只返回固定理由，避免异常消息携带原始命令或密钥。
9. 使用当前环境的 pnpm 11.25.0，并固定工具版本。pnpm 的构建脚本许可只给锁定的
   `esbuild@0.28.2`。pnpm 11 的设置放在 workspace YAML，不额外维护无效的 `.npmrc`。

来源规格、ADR 和计划快照继续保留，不为测试结果改写历史内容。
本轮实际行为以本记录、代码和测试为准；本地进度在计划索引的复现表单独标注。

## 面试时怎么讲

可以用下面这段话开场，再打开演示验证：

> 我在做一个 Coding Agent 的审批服务。第一阶段先解决确定性决策：危险操作先经过守卫，
> 普通操作匹配主人规则，没有依据就交给主人。规则冲突时拒绝优先。
> 我把决策写成纯函数，所以可以在不启动 Agent、不连接飞书的情况下测试危险输入。
> 下一阶段会把这个规则层接到 ACP 请求和主人审批闭环。

三个值得展开的例子：

- **为什么不能只写 `startsWith`？** `/work/project-old` 也以 `/work/project` 开头，
  但不是它的子目录；测试覆盖了这类路径逃逸。
- **为什么命令归一化不能直接用于授权？** 去掉 `cd` 会丢失执行目录，去掉环境变量会丢失
  运行配置，所以显示归一化和允许条件分开检查。
- **为什么保留不支持的语法？** 自己写的解析器容易遗漏 shell 语义。明确拒绝分析复杂写法，
  用更多人工确认换取可解释性。它也不承诺约束脚本内部的操作。

不要把计划中的飞书闭环、幂等和持久化讲成已经做完，也不要声称这是完整的安全沙箱。
